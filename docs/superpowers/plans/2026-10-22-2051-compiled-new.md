# `new` as compiled code — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The primary factory of every class becomes a compiled body on
the class side, and each level's instance initializer one compiled body
that initializes its superclass first through dedicated instructions.
The Rust instantiation walk and road step 6's fast `new` go. Alongside:
- the nested-class accessor's cache hit becomes a guard and one field
  load;
- a declaration without a body becomes the mixin application itself,
  fixing a deviation from the specification.

**Architecture:**
- `Foo x: 1` is an ordinary send. Its cache target is a factory entry
  that now carries a body: `AllocateInstance`, then `InitializeInstance`,
  then `Return`.
- `InitializeInstance` runs the receiver class's level initializer on the
  new instance.
- A level's full initializer (`Mixin::initializer_code`) runs, in order:
  1. checks each `<:` clause's selector (`CheckAppliedClause`);
  2. evaluates the superclass clause's arguments inline;
  3. runs `InitializeSuperclass`: the §6.1 selector check and the arity
     check, then the superclass level's initializer, passing levels
     without code in a loop;
  4. for each `<:` clause, evaluates its arguments and runs
     `InitializeAppliedLevel`, which runs that mixin's own part
     (`own_initializer_code`) at the level the clause added;
  5. its own slots and `initExprs`, answering `self`.
- Every check lives in `interpreter/instantiate.rs` with today's texts.
  `vm.rs` only calls into it.

**Tech Stack:** Rust 1.98.0, `cargo-nextest`.

**Spec:** `docs/superpowers/specs/2026-10-22-compiled-new-design.md`.
Read it before Task 1, together with:
- `docs/design/object-model.md`: "Instantiation", "Mixin application",
  "Class sides and metaclasses", "What a slot access checks";
- `docs/design/execution.md`: "Deciding, then running", "A superclass
  chain is walked iteratively";
- `docs/design/dispatch.md`, about the factory and nested-class targets.

**Decided with the user on 2026-10-22** (the spec's "Decided with the
user"; not reopened):
1. The factory is compiled code with an activation of its own, shaped like
   Squeak's (allocate, run the initializer, return the instance).
2. The initializers are bodies on their mixin, outside the method table,
   reached by dedicated instructions -- never a super send of a hidden
   selector.
3. A class without initializer code pays one factory activation until
   road step 8.
4. A `<:` level reached from outside (through a mirror) is an ordinary class
   of its mixin.
5. The nested-class accessor stays bodiless; its cache entry holds the
   hidden slot's absolute index.
6. Initializers nest one counted activation per level with code; a deeper
   chain gets the ordinary stack-overflow error.
7. The measurements are a record with a tolerance; a large regression stops
   the batch and goes to the user.
8. A declaration without a body is the mixin application itself: its class
   object is the level its last `<:` adds, named for the declaration, with
   the declaration's factory and no class side of its own.

**Refined while planning, stated here for review:**
- **Which factory a class object has.** Every class object reads it
  through its metaclass's class-side mixin. That mixin's factory entry
  (§6.3: "the class side, together with the primary factory method,
  defines the mixin for the metaclass") gives the selector, the arity and
  the body. This replaces `LevelFacts::factory_selector` and
  `factory_arity`, which are application facts.
  - An applied level takes the metaclass of the class its clause *named*:
    its factory is the named class's, which is what §6.1 checks a `<:`
    clause against and what §6.2 gives `I` ("a primary factory method
    with the same selector as m").
  - Nothing changes for a named class with a body. For a body-less named
    class (decision 8) it is what makes `<: M3 x: 5` check `x:`.
  - A class object's `name` follows the same class side. A level that
    `<: M3` adds is named `M3`, as `M3` itself is. Today a level is named
    for its application's mixin, which is the same thing for every class
    with a body.
- **No per-site cache for the initializer instructions.** A target is a
  few field reads (the superclass walk by `steps`, the applied-clause
  field, the application) and one `Rc` clone, the same work
  `push_initializer` does today. A cache would key on facts of the class
  objects, not of one guard, and is left to the JIT. Task 7 measures.
- **The factory body is synthesized, not lowered.**
  `compiler::factory_body(argument_count: u16) -> CompiledCode` emits it
  directly, with no AST and no resolver. Both lowerings and the image
  decoder use this one function, so the image never carries a factory
  body and cannot forge one. The reference lowering has no distinct
  shape to check here.
- **Three initializer bodies per mixin.**
  - `initializer_code` is the full one, steps 1-5 above.
  - `own_initializer_code` is step 5 alone: today's body, unchanged.
  - `standalone_initializer_code` is steps 2, 3 and 5, for a level
    reached from outside (decision 4). It is `Some` only when the
    declaration writes `<:` clauses, since without them it equals the
    full body.
  - A body-less declaration (decision 8) has a full body and an empty own
    part, and needs no standalone one: its class object is never reached
    "from outside" its own declaration.
- **Clause messages are lowered inline** into the full and standalone
  bodies, in the factory scope the resolver already gives them. This
  removes:
  - `Mixin::superclass_message_code`,
  - `MixinApplicationClause::message_code`,
  - `CodeKind::SuperclassMessage`,
  - `FrameKind::SuperclassMessage` and `FrameKind::MixinApplicationMessage`
    (wire tags 5 and 6 retired),
  - the `{…}` argument array and its two walk-only errors ("did not
    evaluate its message arguments to an argument list", and "a clause
    message of class … takes N factory arguments"; Task 3 shows that
    neither can arise any more).

## Review Focus

1. **A clause argument with a side effect, followed by a §6.1 mismatch
   one level up.** The argument's effect must happen, and the error must
   follow it (§6.3 evaluates the message in *i*, then invokes). Task 3
   pins it with the golden
   `spec_6_1_a_clause_argument_runs_before_the_mismatch_fails.ns`.
2. **An image whose row pairs a body with a factory of another arity, or
   omits one of the three bodies.** The load refuses it, and a run never
   panics. Task 2 pins it with `verify_mixins` tests:
   `an_initializer_whose_arity_disagrees_with_the_factory_is_refused` and
   `a_mixin_with_clauses_but_no_standalone_initializer_is_refused`.
3. **A `^` inside a block in a clause argument** (non-local return out of
   the initializer). Today the clause message is a frame of its own. Now
   the argument is part of the initializer, and the return unwinds to
   `instantiate`'s caller as an initializer's `^` in a block does today.
   Task 3 pins it with
   `a_return_inside_a_block_in_a_clause_argument_escapes_instantiate`, in
   `tests/vm_initializer.rs`.
4. **A bulk forward (`become:`) during an initializer**, which replaces
   the instance being initialized. The superclass and applied-level
   invocations run on `self` as today's walk did, and the own-slot guards
   still refuse the old layout. Task 3 runs the existing
   `goldens/library/mirror*` and `vm_initializer.rs` tests unchanged; no
   new test is needed unless one fails.
5. **The nested accessor's cached index after an edit or a forward
   reshapes the enclosing object.** The guard is the receiver's
   application, so a reshaped receiver misses and takes the slow path.
   Task 5 pins it with
   `a_nested_class_hit_after_the_enclosing_object_was_reshaped_takes_the_slow_path`.
