# Debugger Stage 5: Evaluation, Writing Frames, Smart Step Into, Marks and the Memory View — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** At a stop the user evaluates expressions in any program frame (DAP `evaluate`: the Evaluate dialog, watches, hovers), sets variables, sets conditional breakpoints and logpoints, smart-steps into a chosen call or block, restarts a frame or forces it to return, marks objects and names them in later evaluations, looks at a class's instances and an object's referrers, and sees the shipped modules' frames folded -- in the VM's debugging API, the DAP agent, an MCP server through which an agent such as Claude debugs (Task 13a, decided 2026-11-17), and the JetBrains plugin.

**Architecture:** An expression is resolved by a new resolver entry against the stopped body's class chain and the frame's variable table, and compiled as a block whose frame variables are `LoadOuterLocal`/`StoreOuterLocal` (or vector accesses) into the stopped frame, its marked labels its parameters. The debugger makes the closure over the reified stopped frame and pushes it above every live frame with a new `Continuation::Evaluated`; the stop, today the locals of `stop_standing`, becomes state the `Debugger` holds, left with a new `Served::Evaluate` (the run loop reads its frame again, as for `Served::Rebuilt`) and re-entered at the safepoint the evaluation's return requests. The evaluation's base frame ends the handler search and every unwind: an exception no handler above it takes, an abort, a `^` to a home below it and an overrun of its own depth reserve are answered as its result. Restart and force return are unwinds the stop starts, to a frame, through the one unwinder. Conditions and logpoints are evaluations the safepoint runs for a breakpoint the cold decision found conditional. Every new command is a `Command`/`Event` of `debugger/remote.rs`; the agent maps DAP onto them; the plugin adds the platform's evaluator, value modifier, smart step into, drop frame and value marker over the agent, and a memory view of its own.

**Tech Stack:** Rust 1.100.0 (edition 2024), `serde_json` (already `ns-cli`'s), `cargo-nextest`; Kotlin, the IntelliJ Platform's XDebugger API, Gson from the platform; no new external dependency.

**Spec:** `docs/design/debugger.md` -- decisions 3 (smart step into), 8 (evaluation); "Writing a frame", "Evaluation", "Assigning a captured variable", "Evaluation never reaches the VM mirror", "Marking objects", "The memory view", "Folding the shipped frames", "Restart frame and force return", "Smart step into a block", "Hit counts and temporary breakpoints" (the condition before the count), "Values the IDE holds" (pinning), "The JetBrains plugin" (its `Planned:` paragraph), "Planned: the order of building it", stage 5; `docs/design/execution.md`, "The depth limit"; `docs/OPEN-WORK.md`, "Next".

## Global Constraints

- No new external dependency, in Rust or in the plugin. `ns-memory` stays the only crate with `unsafe`.
- `ns-runtime` sees no DAP type; nothing crossing to the agent carries a `Symbol`, `Value`, `Root` or handle. Never `{:?}` a `Value`, never `.unwrap()` an `EvaluationResult`; names are written out; a Newspeak module inline in a test is an `indoc! {"…"}` with the closing `"}` on its own line.
- **No golden, no `run-corpus` outcome, no image and no instruction encoding changes.** `Continuation::Evaluated` is never encoded (no image is written while an evaluation runs): the encoder's exhaustive match answers it with `unreachable!`, and no wire tag is added. `Binding::FrameVariable` is never recorded by `resolve` or `resolve_kernel`.
- **Nothing on the hot path.** A program run without a debugger takes no new branch: a condition, a logpoint and the evaluation's depth limit are read only in `#[cold]` paths (`interpreter/breakpoint.rs`'s decisions, `push_past_the_limit`, the unwinder's arrival and the safepoint). A commit touching `vm.rs`, `interpreter/mod.rs`, `interpreter/sends.rs`, `heap.rs` or `heap/frames.rs` runs `cargo xtask gates commit codegen`, and the codegen budgets hold unchanged.
- **The VM mirror stays a capability.** Evaluation, setting a variable, restart and force return are refused in a frame whose body belongs to a shipped module, with the reason `"the frame is the core library's"`; a withheld value is never marked, never named in an expression and never forced as a return value.
- Evaluation obeys access control as the frame's method does; no send ignores it.
- The evaluation's depth reserve: E = 1,000 counted activations (`EVALUATION_DEPTH_RESERVE`, beside `DEPTH_RESERVE` in `interpreter/mod.rs`); the limit while an evaluation runs is `max(MAX_ACTIVATION_DEPTH, base + EVALUATION_DEPTH_RESERVE)`, `base` the counted depth of the stopped frame.
- A marked label is named in an expression as `<label>_DebugLabel`; a label is an identifier (`[A-Za-z_][A-Za-z0-9_]*`) without the suffix; marks live until unmarked or the attachment ends.
- Refusal reasons are fixed strings, named once as `const`s in `debugger/mod.rs` and matched by the tests: `"the frame is the core library's"`, `"no such frame"` (exists), `"the value is withheld"`, `"<name> is captured by a block made before this point"` (with the name), `"<name> is not assignable"`, `"the expression does not compile: <message>"`, `"a ^ cannot leave an evaluation"`.
- The evaluation's errors: an error answered as an evaluation's result carries the exception's `messageText`-based description (`Heap::describe` of the exception), never `{:?}`.
- DAP lines and columns stay 1-based, columns in UTF-16 code units (`ns_tooling::lines`).
- A `.ns` file edited is formatted with `cargo run -p ns-analyzer -- fmt <paths>`; this plan edits no core-library file.
- Every commit runs `cargo xtask gates commit` (which runs the plugin's `gradlew --no-daemon check`), plus `codegen` as above. The batch ends with `cargo xtask gates end-of-batch` and `cargo xtask gates plugin-verification` (Task 15); every commit before it is work in progress. Subagents run every command in the foreground.
- Comments explain the decision, not the mechanics. A task that builds a `Planned:` part of `debugger.md` rewrites it in the present tense, with its **Built**/**Partial** marker, in the same commit.

## Review Focus

1. **A stop in machine code** (a breakpoint in a loop run 10,000 times, so its body is JIT-compiled and optimized): an evaluation and a `setVariable` there must read and write the frame the interpreter sees, and continuing must give the program's ordinary output with the written value. Pinned in Task 3 (`an_evaluation_in_a_compiled_loop_reads_the_iteration`) and Task 5 (`a_variable_set_in_a_compiled_loop_is_seen_by_the_next_iteration`).
2. **A collection during an evaluation** (an expression that allocates 200,000 arrays): the stop's described values, the marks and the stopped frame must survive the move; the variables view answers the same values after. Pinned in Task 3 (`a_collection_during_an_evaluation_keeps_the_stop_s_values`).
3. **A block the expression stores that outlives the frame** (`holder value: [count]`, then continue until the frame returned, then `holder value value`): it must read the frame's last value, never `nil`. Pinned in Task 3 (`a_block_an_evaluation_stored_reads_the_frame_after_it_returned`).
4. **A conditional breakpoint's condition with a side effect** (`counter increment. counter value > 2`): evaluated exactly once per hit, by the VM, never again by the IDE. Pinned in Task 6 (`a_condition_is_evaluated_once_per_hit`) and Task 14 (`testAConditionIsEvaluatedByTheRuntimeOnly`).
5. **A terminate or disconnect while an evaluation runs** (an expression looping forever): the program must end (terminate) or the evaluation be aborted and the program run on (disconnect), with every `ensure:` block of both run once. Pinned in Task 4 (`a_terminate_during_an_evaluation_ends_the_program`, `a_detach_during_an_evaluation_aborts_it`).
