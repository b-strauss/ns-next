# Closures, non-local return, allocation and the barrier in machine code Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Road step 8's fourth stage on x64. Afterwards a compiled body
exits only at an error, at a poll that found a request, at a
continuation other than `Deliver`, and at an unwind it cannot cut. To
get there, machine code itself allocates, stores through the barrier,
makes closures, calls them, and cuts non-local returns.

**Architecture:** The work comes in three parts, each measured against
the tree before it.

- **4a.** Eden's cursor moves where machine code reaches it, with an
  inline bump whose cold path is a leaf, and the barrier goes inline with
  its four early outs. On top of those come the slots, the vectors,
  `at:put:`, the setters, `AllocateInstance` and the initializers'
  invocations.
- **4b.** `MakeClosure` reifies its frame and allocates the closure
  inline. A closure's activation becomes a compiled call through a stub.
  The outer locals and the futures follow.
- **4c.** A routine of its own cuts a non-local return whose home lies in
  the current stretch. Any other non-local return exits to the one
  unwinder.

**Tech Stack:** Rust 1.98.0, edition 2021; no new dependency.

**Spec:** `docs/design/execution.md`, "Stage 4: closures, non-local
return, allocation and the barrier" (the six decisions there were taken
with the user on 2026-10-30). Read it with "Planned: the deoptimization
contract" ("Returns", "Non-local return and unwinding"), "The closure
keeps its defining activation", "Unwinding", and `docs/design/memory.md`,
"Generations" and "What the collector traces".

## Global Constraints

- **Earlier plans.** Everything in the Global Constraints of
  `docs/superpowers/plans/2026-10-28-1928-jit-sends.md` still holds:
  - `unsafe` appears only in `ns-memory`;
  - names are written out;
  - machine code holds no handle;
  - code is written only through `CodeWriter`;
  - the JIT is compiled in only where `cfg(ns_jit)`, and
    `NS_NEXT_NO_JIT=1` turns it off;
  - `vm.rs` holds no dispatch logic;
  - a cell is written only from its entry;
  - a stub does what `Mutator::act_with_base` does for its target and
    nothing more.
- **Templates and leaves** (CLAUDE.md, "Machine code is a lowering of the
  interpreter's instructions"):
  - A template stores into the frame only after its last decline or exit.
  - A leaf runs no Newspeak code, cannot collect, reads no other
    activation and never pushes.
  - A leaf answers "re-execute" only before it changed anything but a
    send's argument slots.
  - The cut (Task 14) is the one routine that reads and pops other
    activations. Its own rule goes into CLAUDE.md in that task.
- **Machine words.** No word that machine code reads or writes between
  two leaf calls lies in the `Mutator`. Eden's cursor gets an allocation
  of its own in `ns-memory`. New per-application words go in the
  application id table's reservation. New lasting addresses go in the
  entry block's free words 22-28. A lasting word is written only where
  what it names changes, which marks the block stale.
- **The barrier** (CLAUDE.md, "Every store into an existing object goes
  through `heap.rs`'s store accessors and their write barrier"):
  - Every store machine code makes into an object it did not allocate in
    the same template takes the inline barrier.
  - An old allocation is born remembered, so the leaf's old path keeps
    `remember`.
  - `AlignedBytes` data begin at the block's first 32-byte address. An
    inline byte access computes that offset as `heap/object.rs` does.
- **Registers.** No file under `jit/` other than `macro_assembler.rs`
  names a register. A new need is a new named role in `Roles`, held by
  `crates/ns-runtime/tests/jit_architecture_split.rs`.
- **Analysis hooks.** Every new instruction effect, of which none is
  planned, would be declared in `bytecode.rs`'s exhaustive matches.
  `outer_reach_of` is untouched.
- **Goldens.** The goldens' outcomes do not change. A new golden's
  `.toml` is recorded with `NS_NEXT_NO_JIT=1`. Where a recursion
  overflows does not change: a compiled closure call counts exactly as
  the interpreter's push does, control-flow exemption included.
- **Commits.** Commits are conventional, and each ends with the
  `Co-Authored-By:` line naming the committing model and the line
  `Claude-Session: https://claude.ai/code/session_01J94EWdQWbAEZ5QdaZ8vbvi`.
- **Gates.**
  - `cargo xtask gates commit` runs before every commit.
  - `memory` is also run for Task 2.
  - `codegen` is also run for every task touching `vm.rs`,
    `interpreter/mod.rs`, `interpreter/sends.rs`, `heap.rs`,
    `heap/frames.rs` or `bytecode/compact.rs`.
  - `caches` is also run for every task touching
    `interpreter/inline_cache.rs`.
  - `end-of-batch` runs at Tasks 8, 13 and 15, before each measurement.
  - A commit that never saw the end-of-batch gates is work in progress,

- **Stress modes.** Each task's run of every golden under

## Review Focus

1. **A young value stored by machine code into an old object** (an
   object tenured before a loop whose compiled body stores freshly
   allocated objects into it) must be remembered. Otherwise the next
   scavenge reclaims what the old object names. Pinned by Task 3's
   `an_inline_store_of_a_young_value_into_an_old_object_remembers_it`,
   with `NS_NEXT_STRESS_SCAVENGE`'s verification of the remembered set
   over every golden.
2. **A compiled loop that allocates past the scavenge threshold and past
   eden's end with no poll between**, which is straight-line code
   allocating more than 512 KiB. It must request the scavenge, carry on
   up to the ceiling, then allocate old and born remembered, exactly as
   the interpreter does. Pinned by Task 2's
   `machine_code_allocates_past_eden_as_the_interpreter_does`.
3. **A `^` from a block whose home has returned**, or whose home lies
   below an `ensure:` activation, run from compiled frames. The first
   must raise `cannotReturn:`. The second must run the `ensure:` block
   exactly once, in the interpreter's order. Pinned by Task 14's goldens
   `non_local_return_through_ensure.ns` and
   `non_local_return_dead_home.ns`.
4. **A block's activation observed by reflection after machine code made
   and ran it.** Its `enclosingActivation`, the dead creator's program
   counter and its `uncontinuable` flag must read as under
   `NS_NEXT_NO_JIT`. Pinned by Task 9's golden
   `goldens/runtime/jit/reified_frames.ns`.
5. **A recursion through compiled closure calls overflowing the depth
   limit**, both a block that calls itself through a slot and one that
   an inlined `ifTrue:` of the reference lowering runs. It must raise at
   the activation the interpreter raises at, exemption included. Pinned
   by Task 10's golden `goldens/runtime/jit/closure_recursion_overflow.ns`.

### Task 2: Eden's cursor where machine code reaches it, and the bump

**Files:**
- Modify: `crates/ns-memory/src/lib.rs` (`BumpCursor` and its users).
- Modify: `crates/ns-runtime/src/heap/space.rs`, `heap.rs`
  (`allocate_block`).
- Modify: `jit/macro_assembler.rs`, `jit/leaves.rs`, `jit/stubs.rs`
  (`BlockWord::EdenCursor = 22`).
- Test: `crates/ns-memory` unit tests, `crates/ns-runtime/tests/jit.rs`.

**Interfaces:**
- Produces:
  - `ns_memory::SharedCursor`: an allocation of two `Cell<usize>` words,
    top then limit, behind an `Rc` (the machine words' pattern).
    `Reservation` reads and writes its cursor only through it, so
    `bump`, `bump_array`, `bump_up_to`, `set_bump` and `record` keep
    their contracts.
  - `Reservation::bump_cursor_address() -> usize`: the address of the
    top word, the limit word 8 bytes past it.
  - In the entry block, `BlockWord::EdenCursor` holds that address. It
    is lasting, written when the block is made and when the space's
    reservation is replaced, which marks the block stale.
  - The idiom `MacroAssembler::bump_allocate(object: Register, bytes: i32
    or a register, header: u64 word or register, class_word: Register,
    slow: Label)`. It loads top and limit, takes `slow` when
    `limit - top < bytes`, stores the new top, and writes the header word
    and the class word. `object` answers the object's byte offset, which
    is the object's word, as `Value::object` makes it.
  - `Leaf::Allocate` (arguments: the word count and the header and class
    words). It calls `Heap::allocate_block`'s cold decision: request the
    scavenge, bump to the ceiling, or allocate old and remember. It never
    collects and answers the offset. The template's slow path calls it
    and rejoins the fast path's fill.
  - `ns_assembler`: a 32-bit `test_immediate` (`Width::Word32`), so the
    remembered bit 31 tests without sign extension, and
    `shift_right_logical`. Each encoding constant is named and sourced,
    and each encoding is checked against `iced-x86`.

  - In `tests/jit.rs`: `machine_code_allocates_past_eden_as_the_interpreter_does`.

### Task 3: The barrier, the vectors and `MakeArray`

**Files:** `jit/macro_assembler.rs`, `jit/leaves.rs` (`Leaf::Remember`),
`jit/allocation.rs`, `jit/baseline.rs` (the arms `MakeArray`,
`LoadVector`, `StoreVector`), `heap.rs` (`machine_layout` gains
`nursery_end`, `remembered_bit` and the nil word).

**Interfaces:**
- Produces:
  - `MacroAssembler::store_with_barrier(holder: Register, displacement:
    i32, value: Register, scratch: Register)`. It stores the word, then
    applies the early outs in Cog's order:
    1. `value` immediate or nil, which is the tag test plus a compare with
       0;
    2. holder young, `holder < NURSERY_END`;
    3. value old, `value >= NURSERY_END`;
    4. header bit 31 set.

    Then it calls `Leaf::Remember(holder)`, which is `Heap::remember`.
  - The `LoadVector`/`StoreVector` templates check what `store_vector`
    checks: an `IndexablePointers` object, with the index inside it. On a
    mismatch they exit `Reexecute` before any store, so the interpreter
    raises.

### Task 5: The own-slot instructions

**Files:** `heap/application_ids.rs` (a row gains its slot base and its
flags), `jit/allocation.rs`, `jit/leaves.rs` (`Leaf::OwnSlots`),
`jit/sends.rs` (the prologue), `jit/materialize.rs`, `jit/baseline.rs`
(the arms `LoadOwnSlot`, `InitializeSlot`, `InitializeSlotProvisionally`,
`ReturnSlotIfFilled`).

**Interfaces:**
- Produces:
  - **The application id table's row.** It grows from one word to four:
    1. the dispatch id;
    2. the instance header (Task 6);
    3. the slot base;
    4. the flags.

    Flags bit 0 means its slots take §3.1.1's value check
    (`check_value_slot`). The rows are written wherever the row's
    dispatch id is written today.
  - **The frame's guard and entered level.** For code that addresses its
    own slots, the prologue stores the guard "none" and the entered
    level (the current class's application, as the push records it)
    into their header places. `materialize` then writes neither for such
    code.
  - **The own-slot templates.** Each compares the receiver's guard with
    the frame's guard word. On a mismatch it calls `Leaf::OwnSlots`,
    which runs `check_own_slots`'s cold check
    (`interpreter/locals.rs:156-167`), records the guard in the frame and
    answers 0, or EXIT for a receiver without the level. The template
    then exits `Reexecute`.
    - The slot base is read from the entered level's row.
    - `InitializeSlot` with a value check, or with a future value, calls
      `Leaf::Step`, which keeps the interpreter's error and future paths.
      Otherwise it stores with the barrier.
    - `ReturnSlotIfFilled` returns as `return_from` does when the field
      is not the unfilled sentinel.

### Task 9: `MakeClosure` with its frame reified inline

**Files:** `jit/closures.rs`, `jit/baseline.rs` (the `MakeClosure` arm),
`heap.rs` (`machine_layout` gains the frame object's field
displacements and the closure's).

**Interfaces:**
- Consumes: Task 2's `bump_allocate`, Task 8's reified word.
- Produces: the `MakeClosure` template.
  1. It stores the header's program counter.
  2. If the reified word is nil, it allocates the frame object, of
     `frame_field::COUNT` plus the frame's register count fields
     (constant per body), and fills it as `Heap::reify` does:
     - sender nil;
     - home: for a block's code, `closure_home` of the frame's operand,
       which is the captured frame or its home, loaded inline; nil
       otherwise;
     - receiver and current class from the frame;
     - program counter;
     - code id, a constant of the body;
     - kind, a constant;
     - `uncontinuable` false;
     - married, the activation's offset as a number word;
     - registers nil.

     It then writes the reified word.
  3. If the block's `outer_reach > 0`, it sets `retains_registers` in
     the flags word.
  4. It allocates the closure: class word, code id, captured frame,
     feedback base, then the copied values from their registers, with no
     barrier.
  5. It stores into `destination`.

  The code id is constant only while the code's row lives. A body is
  compiled per heap, and a full collection that reclaims a row reclaims
  the code too (`heap/reclaim.rs`), so the test below pins it.

## Part 4c: non-local return

### Task 14: The cut

**Files:** `jit/cut.rs`, `jit/stubs.rs` (the cut's call, like a leaf
call through the shim), `jit/baseline.rs` (the `NonLocalReturn` arm),
`CLAUDE.md` (the cut's rule in the invariant on machine code).

**Interfaces:**
- Produces:
  - **`jit::cut::cut(mutator, frame_word, value_bits) -> CutAnswer`**,
    with `CutAnswer { resume_address: u64, stack_pointer: u64,
    frame_register: u64 }`, or EXIT. `frame_register` is the frame
    register as the home's send left it for its callee, at the home's
    frame plus the send's argument base. The code after the `call`
    takes the argument base off it again. The template calls it with the frame register.
    1. It takes the home as `raise_return` does, reading the closure
       operand's home. With none, or a home not running
       (`frame_is_running`), it answers EXIT.
    2. It walks the stretch's compiled frames by their return addresses,
       as `materialize::walk` does, from the innermost down to the
       entry's frame. At each frame, code with an `unwind_marker` (see
       `CompiledCode::unwind_marker`) makes it answer EXIT, and so does
       reaching the entry's frame without finding the home's activation.
    3. Otherwise, for every frame above the home, innermost first, it
       divorces a reified one as `pop_activation` does and takes a
       counted frame off `DepthCount`. It moves the stack's innermost to
       the home and answers the home's return path: the address after
       the home's send's `call` in the home's code, and the native stack
       pointer at it. Machine code then stores `value_bits` into the
       home's send's destination by jumping to the return address with
       the value in `leaf_result`.
  - **The cut's rule in CLAUDE.md.** It runs no Newspeak code, never
    collects, never pushes, reads only the compiled frames of the
    current stretch, and pops only them.
  - **An EXIT** exits `Reexecute` at the `NonLocalReturn`, so the
    interpreter's `non_local_return` runs the one unwinder.
