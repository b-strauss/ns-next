# The MCP Server and the Trace File — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An agent reaches through `ns-next mcp` what the plugin reads from `--trace-file`: `debug_start` has the child write the trace and the listings into a file the server owns, every stop summary says in one `trace:` line how much it holds, and four tools answer it bounded -- a run-wide overview, one method's journal, a window of one listing, and a filtered list of events. The server serves several numbered sessions at once, so that subagents sharing one server never wait on each other's 600-second waits. Along the way: a class's three initializer bodies get distinct names, `debug_code` answers a window instead of a whole listing, and a program writing to a closed pipe no longer panics.

**Architecture:** The server's main thread reads standard input and answers `initialize`, `ping` and `tools/list` at once; one writer thread owns standard output. Each session has a worker thread that owns its `Session` and reads one inbox channel, into which its DAP reader, the calls routed to it and the server's cancellations and end all arrive -- the shape of the DAP agent's own loop (`debug/`). `debug_start` registers a numbered session and hands the start to that session's worker; every other session tool is routed by `session` to its worker; the trace tools run on a thread per call against the session's `TraceIndex`, never waiting on the worker. The trace file lives in the user's own cache directory under a directory the server claims with a held file lock; the server creates each file and keeps it open, the child writes it through `--trace-file`, and a follower thread indexes it as it grows: offsets of the listings, the events in a compact interned form, and per-body tallies, never a listing's content. Each tool renders its answer as text, the listings as `--print-*` writes them, every cut answer ending in a `Showing X–Y of Z — next: <exact call>` line under a character budget that keeps it below Claude Code's warning.

**Tech Stack:** Rust 1.100.0 (edition 2024), `cargo-nextest`, `serde`/`serde_json` (already `ns-cli`'s), `std::fs::File::try_lock` (stable since 1.89) and `std::os::windows::fs::OpenOptionsExt::share_mode` (safe std API); Kotlin only if Task 2 changes a plugin test's expectation. No new dependency.

**Spec:** The user's decisions of 2026-11-22, which this plan carries into the living documents in Task 12, as present-tense decisions:

1. *The trace goes only to a file.* `debug_start` takes `trace` and `trace_filter` as today, plus `listings` (any of `bytecode`, `code`, `inlining`) and `listing_filter` (patterns, passed as `--print-filter`). The server has the child write `--trace-file` into a file of its own; no trace line enters the output buffer, so the program's output stays the program's. Every summary of a traced session gets one `trace:` line with counts and the file's size. This replaces developer-tool.md decision 9's path for the agent (the lines on standard error) and stage 2's "`debug_start` takes no print option, on purpose".
2. *Tools: a staircase plus a query*, mirroring the tool window's four tabs: `debug_trace` (run-wide overview with top lists, each entry naming a method and a body number and suggesting the next call: most installs, abandonments with revivals, deoptimizations with reasons, optimized methods, declined inlining), `debug_trace_method` (one method's journal: its bodies with numbers, its copies, its events in order with repetitions folded, its sends with inlining outcome and cache state; paged), `debug_trace_listing` (a window of one listing: bytecode, a copy's machine code by index, an inlining plan by index), `debug_trace_events` (events filtered by category, event, reason and method, in order, paged).
3. *Bounds: fixed defaults, pages and windows with a hard maximum, text only.* Overview 10 per list; journal and events 50 per page; a listing window 150 lines; at most 200 entries or 500 lines on request. Every cut answer ends `Showing X–Y of Z — next: <exact call>`. `debug_code` gets the same line window. Text only, no `structuredContent`. Every answer at its maximum stays under Claude Code's 10,000-token warning.
4. *Several sessions per server, with handles, served concurrently.* `debug_start` answers `session: <n>`; every other tool takes an optional `session`, which may be left out while exactly one session is open; with several, a call without it is refused, naming the open sessions with their program and state. A tool waiting up to 600 s in one session does not block another session's calls (subagents of one Claude Code session share one MCP server). No limits: a session, with its child and trace file, lives until `debug_stop` or the server's end, including after its program ended; `debug_stop` ends a running program and deletes the file. The files live in the user's own cache directory, as the shipped sources do, never the shared temporary directory, named per server and session; the server keeps each file open from its creation, and at its start removes the files of servers that are gone.
5. *Names: distinct names at the root, plus body numbers.* A class's three initializer bodies get distinct names everywhere (trace lines, listing heads, the trace file's `name`, and so the plugin). Every trace tool takes a method in the tools' grammar or a body number `#<n>`. A name that matches several bodies: `debug_trace_method` shows them all with their numbers, `debug_trace_listing` asks back, listing the candidates.
6. *(Earlier decision, same batch.)* `ns-next run … | head` must not panic on a closed standard output; fixed with a test.

The scratchpad that held these decisions is temporary: Task 12 is where they become the documents' own.

## Global Constraints

- **The protocol stays hand-written on `serde_json`.** No protocol crate, no async runtime, no channel crate: `std::thread` and `std::sync::mpsc` only. The server knows nothing of the build (`debugger.md`, "Starting it").
- **One writer of standard output.** Every JSON-RPC message the server sends goes through the writer thread (`Responses`), one line, one `write_all` and a flush; no other code touches `std::io::stdout()` in `mcp/`. The server's own words go to standard error through a helper that ignores a write error (`mcp::say`), never `eprintln!`, which panics on a closed stream in a worker thread.
- **A session's DAP state is touched by its worker alone.** No `Mutex<Session>`; calls reach a session only as `Input::Call` in its inbox, served in arrival order -- but `debug_pause`, `debug_stop`, a cancellation and the server's end, which act on a wait in progress (Task 4).
- **The trace tools never wait on a session's worker.** They lock the session's `TraceIndex` only, so that an agent can query the trace of a program that runs or of a wait in progress.
- **The index holds no listing.** It keeps a listing's offset and length and the fields its answers decide by; a window reads the one record again through the server's own handle (developer-tool.md decision 34's rule, for the server).
- **Every answer stays under the character budget**: `ANSWER_BUDGET = 20_000` characters (`mcp/pages.rs`), about 10,000 tokens even at a pessimistic 2 characters a token -- the density of machine code's hex and registers is not measured, so the budget assumes the worst plausible one -- and so at or below Claude Code's 10,000-token warning, never near its 25,000-token cut. A page or window stops at the entry or line that would pass it, and its `Showing` line says where it stopped.
- **Every `next:` is an exact call**: the tool's name and its arguments as one JSON object, `session` always among them, e.g. `next: debug_trace_events {"session":1,"category":"deoptimize","start":50}`. `start` is how many entries or lines are skipped (0-based); `Showing X–Y of Z` counts from 1.
- **Numbers of 1,000 and more are written with `,` separators**; a size in decimal units with three significant digits at most (`980 KB`, `412 MB`, `1.1 GB`).
- **Names written out** in every identifier and every segment (`session_number`, `request_identifier`, never `sid`, `req_id`); comments explain the decision; a Newspeak module inline in a test is an `indoc! {"…"}`; never `{:?}` a `Value`.
- **Tests of the MCP server** use `McpServer::start_plain()` wherever machine code matters. A test whose subject needs a JIT asks a direct `--trace=compile` run first and, on a target without one, asserts what the answer says there (`installs: none`) -- never returns without asserting.
- **Gates.** Every commit runs `cargo xtask gates commit` (Task 2 adds nothing beyond it: `names.rs` and `stack.rs` are not on the `codegen` list). The batch changes the runtime (`ns-cli`, `ns-runtime`), so Task 13 runs `cargo xtask gates end-of-batch`, and `cargo xtask gates plugin-verification` if any file under `editors/jetbrains/` changed; every commit before it is work in progress. Subagents run every command in the foreground with `timeout: 600000` on every long one.

### Task 1: A closed standard output ends the run instead of panicking

`ns-next run Spin.ns | head -1` panics today (exit 101, "failed printing to stdout: … os error 232") in `platform.rs`'s `print!`/`println!`, the transcript leaves `show:` and `newLine`, the only writers of program output.

**Decision** (the user's, 2026-11-22, of the options terminate with status 1, a silent end with status 0, and dropping the output while running on): the first write that finds the standard output closed **terminates the run as `terminate` does** -- a `Signal::Terminate` whose message is `the standard output is closed`, handed to the one unwinder, every pending `ensure:` block run -- and every later write of the process is dropped silently, so that those `ensure:` blocks cannot raise it again. The host reports it as it reports every terminated run: `Uncaught Newspeak error: the standard output is closed` on standard error, exit status 1. Reasons: a pipeline's consumer that has gone means nobody reads, and a program that keeps computing for nobody -- Java's `PrintStream`, which swallows the error, does that, and `java Spin | head` never ends -- is the outcome the shell's SIGPIPE exists to prevent; C programs die by SIGPIPE (status 141, POSIX only), Python raises `BrokenPipeError` and exits 1 after its report, Node emits `EPIPE` and exits 1 when nothing handles it, and Rust's own runtime ignores SIGPIPE and leaves the decision to the program, whose `println!` panics. A termination, not a Newspeak `Error`: an error a program's `on: Error do:` catches would let it go on writing to nobody, and a termination is the existing way a leaf ends a run (`builtins/activation.rs`'s `terminate`), so no new path is added. Status 1 rather than 0, so that `set -o pipefail` sees a producer cut short as it sees a SIGPIPE'd one; the report line rather than silence, because standard error is usually still the terminal and the termination is not the program's own end. The trace sink and the listings on standard error lose their writes rather than the run, as the trace file already does (developer-tool.md, "The trace file"), and the host's own report lines never panic either.

**Files:**
- Modify: `crates/ns-runtime/src/platform.rs` (`stream`: the two writes; a process-wide `static STANDARD_OUTPUT_CLOSED: AtomicBool`), `crates/ns-runtime/src/builtins/mod.rs` (the platform arm, so that the platform primitive can answer a `Signal::Terminate`)
- Modify: `crates/ns-cli/src/trace.rs` (`StandardErrorSink`), `crates/ns-cli/src/entry.rs` (`report_entry_send`, `report_instantiation`, the statistics printers: `writeln!` on `std::io::stderr()`, the error ignored)

### Task 3: Numbered sessions, served concurrently

**Decisions:**
- **Threads, not an event loop.** The main thread reads standard input; `initialize`, `ping`, `tools/list`, an unknown method and a malformed message are answered at once on it, so that `ping` is never queued behind a tool. One writer thread owns standard output (`Responses`). A batch, which revisions before 2025-06-18 allow, is answered as one array once each of its members is answered, by a collector thread over the members' replies, in the members' order.
- **A worker thread per session, one inbox.** A session's worker owns its `Session` and reads one `mpsc` channel, `Input`: the DAP reader thread sends `Input::Dap` into it (`DapClient` no longer has a channel of its own), the router sends `Input::Call`, the server sends `Input::End`. A call arriving while another of the session waits is queued in the worker (`pending: VecDeque<Call>`) and served after it, in arrival order: a session is one DAP conversation, whose requests and stops answer one another in order. Calls of different sessions never share a thread. This is the DAP agent's own shape -- one thread over every input, on one channel (`debug/`) -- applied per session.
- **`debug_start` registers first.** It takes the next session number (1, 2, …, never reused for the server's life), registers the session as `starting` with its label, spawns its worker and hands it the start as its first call; a start that fails removes the session, its number not given again. So a call naming the session while it starts is queued like any other, and Task 4's pause and stop reach a start's wait too.
- **The handle is `session`, an integer.** Every tool but `debug_start` takes it, optional: left out, the one open session is meant; with none open the refusal is today's `no program is being debugged; debug_start starts one`; with several, `2 sessions are open: session 1 (Bounce.ns, stopped), session 3 (CD, running) — pass session`; a number not open, `no session 4 is open: session 1 (Bounce.ns, stopped), session 3 (CD, running)` (or `no session 4 is open; debug_start starts one` with none). The label is the program file's name for a `.ns` file, the directory's name for a project (given as its directory or its `newspeak.json`); the state `starting`, `running`, `stopped` or `ended`, which the worker publishes in the handle (`Mutex<SessionState>`) at every change, so that the registry never asks a busy worker.
- **`debug_start` no longer ends another session.** Its answer's first line is `session: <n>`, the summary after it. Its description states the retention, as MCP's guidance on stateful tools asks: a session lasts until `debug_stop` or the server's end. `debug_stop` answers its summary and a last line `session <n> is closed`, and removes the session; a later call naming it is refused as a number not open.
- **The server's end**: at the end of its input the server sends `Input::End` to every worker, waits for each at most `END_BOUND` plus `STOP_WAIT`, and exits; a worker ending drops its `Session`, which kills the child as today.
- **Shipped sources of two concurrent starts.** `shipped_sources::core_library`'s partial directory is named by process id alone today; two sessions of one server starting together would write the same one. It is named by process id and session number.

### Task 4: A wait in progress answers to pause, stop, cancellation and the server's end

**Decisions:**
- **`debug_pause` and `debug_stop` act on a wait in progress.** A wait loop that takes `Input::Call` of one of them from the inbox acts at once -- sends `pause`, or `terminate` and the kill past `STOP_WAIT` -- and answers it once the program stopped or ended; the waiting call answers the same stop or end. The output since the last answer goes to whichever answers first, as today's `shown` cursor decides. Every other call waits its turn: these two are the ones a debugger's user presses while the program runs.
- **Cancellation (`notifications/cancelled`) is honoured.** MCP's cancellation asks the receiver to stop the request and send no response; a client sends it when its user interrupts a call (the user's Escape in Claude Code). Without it, an abandoned 600-second wait holds its session's queue for nothing. The main thread records the cancelled identifier in `Responses`, which drops a later response to it, and sends `Input::Cancelled(identifier)` to every session's inbox; the session whose running call has that identifier ends its wait at once and answers nothing -- the program goes on running or stays stopped, as an expired wait leaves it --, an evaluation is aborted through DAP `cancel` as its timeout aborts it, and a queued call of that identifier is dropped. A cancelled `debug_start` keeps its session: the program is started, and only the answer is dropped, so that the next call sees it.
- **The server's end ends a wait.** `Input::End` ends any wait and the worker.

**Files:**
- Modify: `crates/ns-cli/src/mcp/session.rs` (the wait loops: `wait_for_stop`, `stop`, `evaluate`, `response`), `crates/ns-cli/src/mcp/worker.rs` (`Input::Cancelled`, the running call's identifier, the pending queue), `crates/ns-cli/src/mcp/responses.rs` (the cancelled set), `crates/ns-cli/src/mcp/mod.rs` (`notifications/cancelled`)
- Test: `crates/ns-cli/tests/mcp.rs`

### Task 5: The server's trace files

**Decisions:**
- **Where.** `<own directory>/traces/`, the own directory the shipped sources already use (`%LOCALAPPDATA%\ns-next`, `$XDG_CACHE_HOME/ns-next`, `~/.cache/ns-next`; `own_directory` moves out of `shipped_sources.rs` into `mcp/own_directory.rs` for both), never the shared temporary directory, where another user could put a file at the path first.
- **Names.** A server claims a name `<process id>-<16 hex digits from the operating system's random source>` (`debug::Token`), so that servers of several Claude sessions, of several users' containers sharing a home, or a process id reused never collide; its files are `traces/<server>/session-<n>.trace`.
- **How a server knows another is gone: a held file lock.** A server first creates `traces/<server>.lock` (`create_new`) and takes `File::try_lock` on it for its whole life, then checks that the path still names a file (else another server's cleanup took it in between, and it claims a new name), then creates `traces/<server>/`. At its start a server removes, for each `*.lock` it can lock itself, that lock's directory and then the lock file, and every directory under `traces/` that has no `.lock` beside it (its lock always outlives it). An exclusive lock is released by the operating system when its process ends however it ends, on Windows (`LockFileEx`) and POSIX (`flock`) alike, so no age guesses at whether a server that has run for days is alive, and nothing beyond `std` is needed. The lock is on a file of its own because a Windows byte-range lock on the trace file would refuse the child's writes.
- **The open handle.** Before the child starts, the server creates the session's file and keeps the handle -- on Windows opened with `share_mode(FILE_SHARE_READ | FILE_SHARE_WRITE)` and without `FILE_SHARE_DELETE`, so that the child's `File::create` (which truncates and writes) succeeds and any other process's delete fails; on POSIX the handle reads on even if the path were unlinked. The child gets `--trace-file=<path>`.
- **Deletion.** The file is deleted when its last holder drops the handle -- the session's `TraceIndex` (Task 6) -- after `debug_stop` and at the server's end; at the server's end its directory and lock file go too.
- **`debug_start`'s new parameters.** `listings`, an array of `bytecode`, `code`, `inlining`, each passed as `--print-bytecode`, `--print-code`, `--print-inlining`; `listing_filter`, an array of patterns, each one `--print-filter=<pattern>`, refused by the server without `listings` (as clap refuses it, but before anything starts). With `trace` or `listings`, the child gets `--trace-file`; nothing of the trace reaches the output buffer, since the file replaces standard error (developer-tool.md decision 20).

### Task 6: The trace index, which follows the file

**Decisions:**
- **A follower thread per traced session** reads the file through the server's own handle from the last complete line's end to the current end, every 50 ms after it grew, the wait doubling to 500 ms while it does not, as the plugin's reader does (developer-tool.md, "The plugin's half"); every tool and every summary first catches up under the same lock, so that an answer at a stop holds everything the stop flushed (decision 25). The thread holds the index weakly and ends when the session drops it. A background follower rather than reading on demand only, because the first question after a long run would otherwise parse the whole file -- a gigabyte in that harness run -- inside the answer.
- **A line is taken only with its `\n`.** The writer's `BufWriter` can put a record's start on disk before its end; a last line without its newline waits for it.
- **Each record is deserialized into a head of the fields the index keeps**, borrowed where it can be, every other field skipped (`serde::de::IgnoredAny`), so that a megabyte of machine code is scanned, never built into a `Value`. The key order is no part of the format, so no prefix is read.
- **What is kept:** the header (architecture, categories, listings); each `body` record but its `statements` (name, family, module, source, range, `placed`, checksum, sends); each event compact -- its record's offset, category, event word and reason interned, its body, the body numbers of `spent-by`, `in-body`, `callee`, its key and entered interned, its fields written once as the trace's text after the body (`trigger=call bytes=1216`, every body field `{#12}`, a name put in its place when shown), interned, so that a fold compares two events by one number; each listing as its kind, body, tier, key, entered, bytes, outcome, offset and length; the byte count read. Per body (`BodyTally`): the counts the overview ranks by (installs by tier, abandoned with the exits summed, revived by `by`, deoptimizations by event and reason, optimized copies by key with their last bytes, declines as callee and as compiler), the indexes of its events, of its `code` and `inlining` records in file order, and of the family's `bytecode` record; per send of a body, the latest inlining decision and cache transition, kept as the plugin's `TraceRun.sends` keeps them.
- **The format's constants are the writer's**: `trace_file::FORMAT` and `VERSION` become `pub(crate)`; a header of another format or version ends the reading with `the trace file is no ns-next trace` / `the trace file has version <n>; this server reads version 1` (a `runtime` may name another binary), a line that is no record with `line <n> of the trace file is no record: <error>`, and every later answer says it after what was read before.

### Task 8: `debug_trace_method`, a method's journal

**Decisions:**
- **Parameters:** `debug_trace_method(session?, method, part?, start?, count?)`. `method` is a name in the tools' grammar or `#<n>` (`TraceIndex::bodies_named`). The answer covers every body the name matches: a method's root and its blocks, each version's and each edited body's -- they are listed, never asked back about (decision 5).
- **What it says, in this order:** a head naming the method, its module and version, its file and line; `bodies:` each with its number, its kind and its first line; `copies of #n:` for each body with machine code -- by tier and, for optimized code, by key and entered, each with how many installs and the `code` record indexes they are (`code 1–1,100`), the indexes `debug_trace_listing` takes, and the `inlining` indexes beside an optimized key; `inlined into:` the bodies that inlined it and how often, and its declines as a callee by reason; `events`, a page; `sends`, a page.
- **Folding.** The events of the bodies, in file order, each written `#<n> [<category>] <event> <fields>`, are folded greedily: at each position, the shortest cycle of one to four events that repeats at least twice in a row, compared by their interned texts, is written once in parentheses, joined by ` → `, followed by `×<repetitions>`; a page counts folded entries, and the head says how many events they fold. So `compiled → abandoned → revived` repeated 554 times is one entry.
- **Sends** of each body, in bytecode order: the 1-based line and column of the call, the selector's text, and the latest inlining outcome and cache state. The selector's text comes from the trace file itself: each `sends` entry of a `body` record gains an additive field `name`, the selector as the compiled send names it (`trace_file.rs`'s `body_record`, from the send's selector symbol), so that no tool reads source and an edited or shipped body names its sends as well (decided by the controller on 2026-11-22: `debugger.md`'s "No tool reads source" stands). The field is documented in developer-tool.md's "The trace file" and pinned by `trace_file.rs`'s tests; the plugin's reader ignores a field it does not know and needs no change. Where an older record has no `name`, the send is written `send`.
- **`part`** is `events` or `sends`. Without it, the head, the first page of events and the first page of sends; with it, that part alone from `start`. Each cut part ends in its `next:`.
