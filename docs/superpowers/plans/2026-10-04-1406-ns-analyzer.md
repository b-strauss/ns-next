# The Analyzer Crate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One binary for everything that looks at Newspeak without running it — the language server, the token dump, `parse`, `parse-corpus`, `disasm`, `inspect`, later a formatter, heap-dump and JIT inspection — beside `ns-next`, which runs, benchmarks and builds.

**Architecture:** The crate `crates/ns-lsp` becomes `crates/ns-analyzer`, its binary `ns-next-analyzer` with subcommands (`lsp`, `dump-tokens`, then `parse`, `parse-corpus`, `disasm`, `inspect`). The helpers both binaries need — loading and resolving a source file, collecting `.ns` files, printing diagnostics — move out of `ns-cli` into a new library crate `crates/ns-tooling`, which depends only on `ns-syntax` and `ns-runtime`, so the language server's dependencies never reach `ns-next` and nothing is copied.

**Tech Stack:** Rust 1.98, `clap` (already a workspace dependency of `ns-cli`), `cargo-nextest`, the JetBrains plugin (Kotlin, Gradle).

**Spec:** decided with the user on 2026-10-04 (no spec file):
- Crate `ns-analyzer`; only the binary carries `ns-next-`: `ns-next-analyzer`. `ns-next-analyzer lsp` starts the language server; `ns-next-analyzer fmt` comes later with the formatter (no placeholder now).
- Everything in `ns-next` that is not run, build or compile moves to the analyzer: `parse`, `parse-corpus`, `disasm`, `inspect`. `ns-next` keeps `run`, `run-corpus`, `load`, `bench`, `build`. Later: heap dump, image and JIT inspection go to the analyzer.
- Shared helpers live in a new small crate (`ns-tooling`).
- One branch, `feature/ns-analyzer`, for the rename and the move.

## Global Constraints

- No behaviour change of any program: every golden, `run-corpus` and the benchmarks unchanged. The moved commands keep their arguments, output and exit statuses; only the binary that offers them changes.
- `ns-next-analyzer` with no argument or an unknown command prints its usage to stderr and exits failing; it never starts the server without `lsp`.
- The language server's dependencies (`lsp-server`, `lsp-types`) stay in `ns-analyzer`; `ns-cli` (`ns-next`) never depends on `ns-analyzer`. `ns-tooling` depends on `ns-syntax` and `ns-runtime` only (and `std`).
- The analyzer inspects and never runs a program: `disasm` compiles, `inspect` decodes an image; neither executes Newspeak. `CLAUDE.md`'s rule that `ns-lsp` "never starts the VM" becomes this rule for `ns-analyzer`.
- No identifier, comment or document keeps the old names (`ns-lsp`, `ns_lsp`, `ns-next-lsp`) outside `docs/superpowers/plans/` (plans stay as written); documents describe the current state, never "renamed from".
- `ns-runtime` and `ns-analyzer` forbid `unsafe`; `ns-tooling` forbids it too.
- Names written out; comments explain decisions.
- Per-commit gates (after Task 1 the names below hold):
  ```bash
  cargo fmt --all
  cargo clippy --workspace --all-targets
  cargo nextest run --workspace --exclude ns-analyzer
  cargo test --workspace --exclude ns-analyzer --doc
  cargo run -p ns-analyzer -- parse-corpus corpus/modules   # "parsed 211, failed 0" (before Task 3: cargo run -p ns-cli -- parse-corpus …)
  cargo nextest run -p ns-analyzer
  ./editors/jetbrains/gradlew -p editors/jetbrains check
  ```
  Every command in the foreground. End-of-batch gates (`finishing-a-batch`) once at the end, with `verifyPlugin buildPlugin`, because the bundled binary changes.
- Commits: conventional (`refactor:`, `docs:`), ending with the `Co-Authored-By:` line naming the committing model and `Claude-Session: https://claude.ai/code/session_014iiGvJnqAeLJtzhwKA6Poa`.

## Review Focus

1. A user's plugin setting pointing at an old `ns-next-lsp` binary: the plugin now passes `lsp`, which the old binary ignores (it starts the server anyway) — harmless; a setting pointing at the new binary works. State it in editor-support.md.
2. `ns-next parse …` (and the other moved commands) in scripts and documents: every mention in the repository moves to `ns-next-analyzer` (test in Task 3: `git grep` finds no `ns-next parse`, `ns-next disasm`, `ns-next inspect`, `ns-next parse-corpus` outside plans).
3. The bundled plugin archive contains `bin/<os>-<arch>/ns-next-analyzer[.exe]` and no `ns-next-lsp` (checked in Task 4 after `buildPlugin`).
4. The analyzer's usage and exit status for no argument and an unknown command (test in Task 1).
5. The moved commands' existing tests keep their assertions, now against `ns-next-analyzer` (Task 3).
