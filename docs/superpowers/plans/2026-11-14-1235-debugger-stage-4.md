# Debugger Stage 4: The DAP Agent and the Plugin's Debugger — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `ns-next run --debug` / `--debug-connect` (and `ns-next load` alike) speak the Debug Adapter Protocol over the debugging API, and the JetBrains plugin debugs a Newspeak program from its existing run configurations: line breakpoints with block variants and pass counts, method and exception breakpoints, the steps by line, run to cursor, pause, the stack, paged variables, the embedded modules' source, terminate, the second Stop that kills, and disconnect.

**Architecture:** The VM side gains four small things: an answer for every command dropped between runs, hit conditions counted at the `Breakpoint` arm's decision, a `ModuleText` command for the current text of a module, and a public compile of a module's breakable statements for the analyzer; `DebugRemote` splits into a control half and an event half so the agent can pump events on a thread of its own. `ns-cli` gets a `debug/` module: the wire (Content-Length framing over `serde_json`), the DAP types it uses, the agent (one thread over a unified input channel fed by a socket reader and a VM-event pump), and the host link the interpreter thread checks between runs. `ns-memory` gives the token its randomness; `ns-tooling` takes the analyzer's `LineIndex` so the analyzer and the agent share one offset/line conversion. The analyzer answers `newspeak/breakableLines`. The plugin gets a DAP client of its own (Gson, which the platform bundles), a debug runner that listens and starts `ns-next run --debug-connect`, an `XDebugProcess`, and three breakpoint types.

**Tech Stack:** Rust 1.98.0 (edition 2021), `serde_json` (already `ns-cli`'s), `windows-sys` and `libc` (already `ns-memory`'s), `cargo-nextest`; Kotlin 2.4.10, the IntelliJ Platform's XDebugger API, Gson from the platform; no new external dependency.

**Spec:** `docs/design/debugger.md` -- decision 6; "Commands while the program runs" (the stage-4 paragraph), "A breakpoint names a source position" (the breakable places), "Hit counts and temporary breakpoints", "Launching, the start and the end", "Threads", "Planned: the JetBrains plugin", "Planned: the order of building it", stage 4; decision 4's last paragraph (stepping by line); `docs/OPEN-WORK.md`, "Next" (the measurement once `--debug` exists, the unknown breakpoint id).

## Global Constraints

- No new external dependency, in Rust or in the plugin (`CLAUDE.md`, "Add no new external dependency"). `ns-memory` stays the only crate with `unsafe`; `ns-runtime`, `ns-tooling` and `ns-analyzer` forbid it.
- `lsp-server`/`lsp-types` never reach `ns-next`; `ns-runtime` sees no DAP type, only the debugging API's. Nothing crossing to the agent carries a `Symbol`, `Value`, `Root` or handle.
- Names are written out (`CLAUDE.md`, Conventions); a Newspeak module inline in a test is an `indoc! {"…"}` with the closing `"}` on its own line; never `{:?}` a `Value` nor `.unwrap()` an `EvaluationResult`.
- **Nothing on the hot path**: a hit condition is read only in `interpreter/breakpoint.rs`'s `#[cold]` decision; no instruction, no golden, no `run-corpus` outcome and no image changes. A program run without `--debug` takes no new branch.
- The program's standard streams stay its own: the agent writes nothing to stdout ever, and to stderr only the one listening line `ns-next: debugger listening on 127.0.0.1:<port>, token <32 lowercase hex digits>` before the program writes anything; the agent's own messages go to the client as `output` events (category `console`).
- DAP lines and columns are 1-based (`linesStartAt1`/`columnsStartAt1` true, the only form the agent supports; an `initialize` asking 0-based is answered with an error); columns count UTF-16 code units, as the analyzer's LSP positions do.
- The token: 16 bytes from the operating system, printed as 32 lowercase hex digits, compared in constant time; only `initialize` is answered before an `attach` that presents it; a wrong or missing token gets an error response, the connection closed, the next one awaited.
- A `.ns` file edited is formatted with `cargo run -p ns-analyzer -- fmt <paths>`; core-library files stay LF; editing `Kernel.ns` is not part of this plan.
- Every commit runs `cargo xtask gates commit` (which includes the plugin's `gradlew --no-daemon check`); also `memory` for a commit touching `crates/ns-memory`, `analyzer` for one touching `crates/ns-analyzer`. The batch ends with `cargo xtask gates end-of-batch` and `cargo xtask gates plugin-verification` (Task 15); every commit before it is work in progress. Subagents run every command in the foreground.
- Comments explain the decision, not the mechanics. A task that builds a `Planned:` paragraph of `debugger.md` rewrites it in the present tense in the same commit.

## Review Focus

1. **A `terminate` that arrives between two host runs** (a project: manifest, root, `main:args:`): the program must end before `main:args:` runs, with the terminated program's exit status and an `exited` event, never run on. Pinned in Task 8 (`a_terminate_between_runs_ends_the_program_before_main`).
2. **A client that disconnects while the program is stopped**: the program must run on to its end with its own output and exit status, every breakpoint gone, in both modes; in the listening mode a second client must be able to connect and stop it again. Pinned in Task 8 (`disconnecting_while_stopped_lets_the_program_finish`, `a_second_client_connects_after_the_first_disconnected`).
3. **A stop whose `hitBreakpointIds` name a breakpoint the IDE replaced meanwhile** (a `setBreakpoints` answered after the stop it changed): the agent must not fail or drop the stop; ids it no longer knows are left out of `hitBreakpointIds`. Pinned in Task 9 (`a_stop_naming_a_replaced_breakpoint_is_reported_without_it`).
4. **Non-ASCII text before a breakpoint or a frame** (a string literal with `é` and an emoji on an earlier line and on the same line): lines and UTF-16 columns must round-trip between the IDE and the VM's byte offsets. Pinned in Task 2 (`line_index_counts_columns_in_utf16_code_units`) and Task 9 (`a_frame_after_non_ascii_text_reports_its_line_and_column`).
5. **A module the program built lazily or a shipped module on the stack** (a frame in `Kernel.ns` under a step into with the shipped filter off): the frame must name a source the client can open (`sourceReference`), whose text is the module's current text, and a second stop must not resend unchanged text. Pinned in Task 4 (`module_text_is_answered_once_per_revision`) and Task 9 (`a_shipped_frame_is_shown_through_a_source_reference`).
