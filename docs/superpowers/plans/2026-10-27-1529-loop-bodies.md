# Real Newspeak bodies for `whileTrue:`, `whileFalse:` and `do:`: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `Closure>>whileTrue:`, `Closure>>whileFalse:` and `Array>>do:` become Newspeak loops instead of forwarders to trampoline-step leaves, so that road step 8's baseline JIT can see through them, and the leaves and their continuation machinery go.

**Architecture:** Each method's body is a loop the compiler already inlines (`docs/design/compiler.md`, "Control-flow inlining"): a back-edge over literal blocks, whose sends (`value`, `value:`, `at:`) are ordinary virtual sends. Nothing a program can see changes; the existing goldens pin that. The Rust side loses three mirror rows, `WhileLoop`, `DoLoop`, `LoopAction`, three `Continuation` variants and `Closure`'s private `valueOf:` and `valueOf:with:`.

**Tech Stack:** Newspeak (`crates/ns-runtime/core-library/Kernel.ns`), Rust (`crates/ns-runtime`), cargo-nextest.

**Spec:** [core-library.md](../../design/core-library.md), "Planned: real bodies for control flow and `do:`, before the baseline JIT" (what must be kept); the decisions L1-L5 agreed with the user on 2026-10-27, recorded here. Prior art: Primordial Soup's `Closure>>whileTrue:`/`whileFalse:` (`prior-art/primordialsoup/newspeak/KernelForPrimordialSoup.ns:746-761`, `^[self value] whileTrue: [action value]`) and `Array>>do:` (`:2574`); SOMns's recursive `whileTrue:` (`prior-art/somns/core-lib/Kernel.ns:637`) is rejected, since every iteration would be an activation against the depth limit.

- **L1.** `whileTrue: body` is `^[self value] whileTrue: [body value]`, `whileFalse:` likewise; Primordial Soup's shape. The inlined loop's guard signals the same `NonBooleanReceiver` (`interpreter::unwind::non_boolean_condition`), `self value` and `body value` the same arity errors the leaf did, and a future body is seen through by the send itself.
- **L2.** `Array>>do: action` reads its size through the leaf, `count = vmMirror collectionSize: self ifFail: [^super do: action]` (as `ByteArray>>do:` does, `Kernel.ns:4346`, so that a payload-less subclass instance goes to `Collection>>do:` and never recurses through `Collection>>size`), then walks with an explicit inlined `whileTrue:` loop sending `action value: (self at: index)`, one activation per element; not `1 to: count do:`, which is a real send to `Number>>to:do:` and costs a second activation per element. Answers the receiver.
- **L3.** No reachable behaviour changes. The leaf's "a receiver whose shape changed under the walk ends it" (`builtins/collections.rs`, `element_step`) cannot happen: an `Array` is a builtin instance, which the bulk forward refuses on either side (`builtins/reflection.rs`'s `may_be_forwarded`), so no golden is added for it.
- **L4.** Measured with the `measuring-performance` skill's protocol against `master` (`be211fe8`). What the code can fix is fixed; the residue that comes only from the extra sends of a Newspeak loop before a JIT is accepted, as decided on 2026-09-22, and recorded in `execution.md`. A new microbenchmark, `benchmarks/micro/bench_while.ns`, runs non-inlined loops; `bench_do.ns` stays the protocol's out-of-tree program.
- **L5.** Docs describe the new state; `OPEN-WORK.md`'s "Next" moves on to road step 8; `PROGRESS.md` gets the entry.

## Review Focus

- **A receiver block that declares parameters, held in a variable** (`[:x | true]` sent `whileTrue:`): must signal the `ArgumentError` 'wrong number of block arguments: block takes 1, got 0' exactly once, before any body runs; Task 1 adds the golden.
- **A body that answers a non-Boolean only after some iterations, with `whileFalse:`**: the guard of the loop inside `whileFalse:` must signal `NonBooleanReceiver` with the same text the `whileTrue:` goldens record; Task 1 adds the golden.
- **A payload-less instance of a user subclass of `Array` sent `do:`**: must reach `Collection>>do:`'s `subclassResponsibility`, not recurse until the depth limit; Task 2 adds the golden.
- **An empty `Array` sent `do:` with a block of the wrong arity, or with `nil`**: answers the array and sends nothing, as the leaf did; Task 2 adds the golden.
- **`do:` whose block makes a non-local return or signals** (a `^` out of the action, an exception handled outside): the walk ends there and nothing after it runs; existing goldens under `goldens/language/block/` and `goldens/library/collection/` cover the `^`; Task 2 adds the signal case to its golden.

### Task 0 (added 2026-10-27 during Task 1, decided with the user): a loop in the reference lowering

The reference lowering inlines nothing, so under it `Closure>>whileTrue:`'s body `[self value] whileTrue: [body value]` is a send to itself and recurses until the depth limit (`run-corpus`'s reference runs failed). **L6.** For a `whileTrue:`/`whileFalse:` send that `control_flow::recognize` accepts, `compiler/reference.rs` emits a naive loop: both blocks real closures, made once; each turn a `SendInlinable` of `value` to the condition, `JumpIfNotBoolean` to a `SignalNonBoolean`, the exit branch, a `SendInlinable` of `value` to the body, the back edge; the loop answers nil. `check_shape` admits the loop's branches only (the back edge the one backward jump). `push_step` exempts a block a `SendInlinable` activates with the send's own arguments from the depth count, as it exempts a control-flow step's, so both lowerings still count alike (`goldens/runtime/depth-limit/recursion_through_a_literal_loop_counts_alike_under_both_lowerings`). Built in the same commit as Task 1; Task 4 documents it in `compiler.md` ("The reference lowering", "What it emits", "How the limit counts").
